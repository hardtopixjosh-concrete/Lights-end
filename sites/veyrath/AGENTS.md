# VEYRATH working instructions

Before planning or changing the game, read `GAME_REFERENCE.md` at the workspace root. It is a short index (rules, workflow, current state). Then read only the `docs/reference/` segment(s) its table lists for the area you are changing. Read every segment only when the user asks for a full-game review. Read the relevant original PDF pages as well when implementing a mechanic or interpreting its visual direction. `docs/pdf-design-transcript.txt` is a searchable convenience copy; the PDF remains the original source.

Before choosing effects, pickups, item icons or hazards, consult `docs/ASSET_CATALOG.md` and its exact `docs/assets/inventory.json` source index. All 15 supplied packs in `Visuals/` and `objects pickups visuals/` are cataloged there, with representative contact sheets, variants, dimensions, frames, duplicates and local license summaries. Preserve the ZIPs; prepare only selected assets for the game. The user approved the orange Ground Slam shockwave from Sci-fi FX Pack 1. Pack contents do not establish new game mechanics.

The user's latest workflow preference is larger, coherent feature batches and faster playable progress, with polish later. This supersedes the earlier one-small-ability-per-review workflow. Implement related features together, publish once per batch, and update the reference. Do not stop for review/approval after every small feature. Preserve the PDF/chat decisions and use actual assets; temporary shapes are appropriate for telegraphs/debugging.

Testing preference (October 14, latest): verify only essentials for each feature batch. Use one focused integration smoke check and a brief visual check where needed. Run broader checks only for a concrete failure or major integration risk. Do not repeat successful checks during packaging or duplicate local and production passes. Prioritize working gameplay over polish and exhaustive testing.

Authority order: latest explicit user decision > recorded chat decisions and PDF annotations > unannotated PDF confirmed design > PDF proposals > implementation defaults. Record new user decisions in `docs/reference/decisions.md`, noting the replaced rule, date, and affected systems. Do not silently promote proposed balance values to approved requirements. Flag unresolved contradictions rather than inventing a resolution.

After each implementation step, append a build-log entry to the matching `docs/reference/log-*.md` with actual behavior, checks performed, limitations, outstanding review, and next step. Update **Current state** in `GAME_REFERENCE.md` when behavior changes. Record user decisions in `docs/reference/decisions.md`. Keep planned features distinct from implemented ones. Keep code data-driven and separate input, simulation, rendering, UI, and save state as those systems grow. Preserve the Sites ID in `sites/veyrath/.openai/hosting.json`; do not create another Site for this project.

The asset ZIPs and original PDF are source materials. Preserve them. Ship only the assets the current milestone needs, not the full packs or design PDF. Do not commit credentials, runtime data, or ZIP packs to the Site source repository.

Latest publishing preference (October 17): for finished Claude updates, read only this index and the newest relevant notes, preserve the implementation, sync references and publish promptly. Reuse recorded checks; additional checks only for a concrete failure or packaging risk. Deeper catch-up waits for implementation/review work.



Latest delivery workflow (October 19, explicit user decision): preserve original artwork/audio quality. Never reduce resolution or apply lossy recompression to fit hosting limits. Do not publish the old full-media static archive. Verify the upload receipt matches the pinned release before deployment. If the uploader reports unchanged=true, skip redundant packaging/deployment. Preserve existing Site identity, audience, launcher origin, saves and old release objects for rollback.

Latest publish-only preference (October 19, user): when asked to update/publish completed files, upload changed files and activate the release without additional sound, gameplay, smoke, syntax or visual checks. Minimize tool calls, reading and usage. Retain required content hashing, upload-receipt matching and native deployment confirmation. Investigate only an actual upload/deployment failure.
